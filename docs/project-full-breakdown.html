Главная идея проекта

Сервис называется search-trends. Его задача похожа на блок интернет-магазина "Сейчас ищут": он получает поток поисковых запросов, считает популярность запросов за последние несколько минут и отдает топ через HTTP.

Входные данные приходят из Kafka. Kafka здесь играет роль очереди/журнала событий: другие сервисы публикуют туда JSON-сообщения вида {"query":"iphone 15"}, а этот сервис читает их.

Результат можно получить по HTTP: GET /top?limit=10. Ответ содержит окно подсчета и список запросов с количеством. 

{
  "window": "5m0s",
  "items": [
    {"query": "iphone 15", "count": 2},
    {"query": "sneakers", "count": 1}
  ]
}

Архитектура простыми словами

Проект разделен на слои. Это не случайные папки: каждый слой отвечает за свою часть работы.

Слой Где лежит За что отвечает
Composition root cmd/main.go Собирает приложение: конфиг, хранилище, метрики, Kafka, HTTP сервер.
Config internal/config Читает переменные окружения и проверяет, что значения корректные.
Domain internal/domain/trends Описывает главные понятия предметной области: поисковый запрос, запись топа, ошибки.
Application internal/application/trends Содержит сценарии: принять событие, получить топ, управлять стоп-листом.
Adapters internal/adapter/http, internal/adapter/kafka Связывает внешний мир с приложением: HTTP-запросы и Kafka-сообщения.
Infrastructure internal/infra Конкретные реализации: память для хранения трендов, Prometheus-метрики.
Главная мысль: бизнес-логика не должна знать, пришли данные из Kafka, HTTP, файла или теста. Поэтому use case работает с интерфейсами, а не с конкретной Kafka или конкретной базой.

Что происходит во время работы

1. Запускается main().
2. Загружается конфиг из ENV: адрес HTTP, Kafka brokers, окно подсчета.
3. Создается in-memory хранилище со скользящим окном.
4. Создается счетчик метрик.
5. Создаются use case: ingest, query top, stop-list.
6. Стартует Kafka consumer и начинает читать сообщения.
7. Стартует HTTP server и принимает запросы.
8. При SIGINT/SIGTERM сервис аккуратно выключает HTTP и Kafka.

Путь одного поискового события

  1. В Kafka приходит JSON-сообщение.
  2. internal/adapter/kafka/consumer.go читает сообщение.
  3. JSON превращается в eventDTO.
  4. Consumer вызывает IngestEventUseCase.Handle.
  5. Use case нормализует запрос через domain.NewSearchQuery.
  6. Use case вызывает store.Add.
  7. MemoryStore кладет событие в нужный временной бакет.
  8. Метрики получают accepted или rejected.

Путь HTTP-запроса /top

  1. Клиент вызывает GET /top?limit=10.
  2. HTTP adapter проверяет limit.
  3. HTTP adapter вызывает QueryTopUseCase.Handle.
  4. Use case вызывает store.Top.
  5. MemoryStore очищает старые бакеты, при необходимости пересобирает snapshot и возвращает top-N.
  6. HTTP adapter кодирует ответ в JSON.

cmd/main.go

Это входная точка приложения. Файл не содержит сложной бизнес-логики. Его задача - собрать все части вместе и управлять жизненным циклом сервиса.

Строка package main

В Go исполняемая программа должна иметь пакет main и функцию main(). Именно с нее начинается выполнение бинарника.

Блок import

Стандартные пакеты: context, errors, log/slog, net/http, os, os/signal, syscall, time.

Локальные пакеты проекта подключаются с псевдонимами: например httpadapter для internal/adapter/http. Псевдоним нужен, чтобы название было понятнее и не конфликтовало со стандартным net/http.

Создание logger

logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))

Создается structured logger. Он пишет JSON в stdout. Для Docker и Kubernetes это удобно: логи можно собирать централизованно.

Загрузка конфига

cfg, err := config.Load()
if err != nil {
  logger.Error("load config", "err", err)
  os.Exit(1)
}

config.Load() читает ENV. Если конфиг плохой, сервис не стартует. Это правильно: лучше упасть сразу, чем работать с некорректными параметрами.

Создание store и metrics

store := infratrends.NewMemoryStore(cfg.Window, cfg.BucketResolution, cfg.MaxQueryPerBucket)
sink := metrics.NewSink()

store хранит тренды в памяти. sink считает метрики: сколько событий пришло, сколько принято, сколько отклонено, сколько было malformed.

Создание use case

ingestUC := apptrends.NewIngestEventUseCase(store, sink)
queryUC := apptrends.NewQueryTopUseCase(store)
stopListUC := apptrends.NewStopListUseCase(store)

Use case - это сценарий приложения. Здесь создаются три сценария: принять событие, получить топ, управлять стоп-листом.

Контекст завершения

rootCtx, cancel := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
defer cancel()

rootCtx отменится, когда процесс получит Ctrl+C или сигнал завершения от Docker. Это основа graceful shutdown.

Запуск Kafka consumer

В kafkaadapter.Start передаются настройки Kafka, use case приема события, метрики и logger. Если Kafka client создать не удалось, сервис завершает работу.

HTTP server

httpadapter.NewServer создает роуты. Затем стандартный http.Server получает адрес, handler и timeout-ы. Timeout-ы защищают сервер от слишком медленных клиентов.

Goroutine для HTTP

serverErrCh := make(chan error, 1)
go func() {
  ...
}()

HTTP-сервер должен работать параллельно с ожиданием сигнала завершения. Поэтому он запускается в отдельной goroutine, а ошибка передается через channel.

select

select ждет первое из двух событий: либо пришел shutdown signal, либо HTTP-сервер сам завершился с ошибкой.

Graceful shutdown

Создается отдельный shutdownCtx с timeout 10 секунд. За это время HTTP-сервер должен завершить активные запросы. После этого закрывается Kafka consumer, который делает финальный commit offset-ов.

internal/config

Конфиг отвечает за все настройки, которые приходят извне. В Docker они задаются через environment, локально - через переменные окружения.

config.go

type Config struct

Структура собирает все параметры приложения: HTTP-адрес, Kafka brokers, topic, group id, длину окна, размер бакета и лимит одинаковых запросов на бакет.

Load()

Главная функция пакета. Она последовательно читает WINDOW, BUCKET_RESOLUTION, MAX_QUERY_PER_BUCKET, проверяет, что значения положительные, и собирает Config.

Важная проверка: WINDOW должен быть больше или равен BUCKET_RESOLUTION. Иначе окно меньше одного бакета, а это ломает смысл sliding window.

getenv

Маленький helper: если переменная окружения есть и не пустая - вернуть ее; иначе вернуть fallback.

splitCSV

Разбивает строку брокеров по запятой: "a:9092, b:9092" превращается в []string{"a:9092", "b:9092"}. Пустые элементы отбрасываются.

getDuration

Умеет читать длительность двумя способами: нормальный Go-формат 5m, 1s, 500ms или просто число секунд, например 300.

getInt64

Читает целое число и требует, чтобы оно было не меньше 1. Используется для MAX_QUERY_PER_BUCKET.

config_test.go

Тесты проверяют default-значения, CSV brokers, ошибки парсинга, ситуацию когда окно меньше resolution, некорректный integer и поддержку "число как секунды".

t.Setenv безопасно ставит ENV на время теста. Helper clearEnv сначала сбрасывает все важные переменные, чтобы тесты не зависели от окружения разработчика.

internal/domain/trends

Domain - самый внутренний слой. Здесь нет HTTP, Kafka, Docker или Prometheus. Только понятия предметной области.

event.go

SearchQuery

SearchQuery хранит строку запроса в приватном поле value. Поле приватное, потому что нельзя дать любому коду записать туда что угодно. Создавать запрос нужно через NewSearchQuery.

NewSearchQuery(raw string)

Это constructor/value object factory. Он нормализует запрос:

  1. strings.TrimSpace убирает пробелы по краям.
  2. strings.ToLower приводит к нижнему регистру.
  3. strings.Fields разбивает по любым пробельным символам.
  4. strings.Join(..., " ") склеивает обратно одним пробелом.
  5. Если после этого строка пустая, возвращается ErrEmptyQuery.

Поэтому " iPhone 15 ", "IPHONE 15" и "iphone 15" становятся одним и тем же запросом.

String() и IsZero()

String() возвращает нормализованную строку. IsZero() проверяет пустое значение, например если кто-то создал var q SearchQuery без constructor-а.

SearchEvent

Структура описывает событие поиска: сам запрос, пользователя, request id, timestamp и source. Сейчас в ingest используется только query и timestamp, а остальные поля оставлены как модель события для будущего антифрода, трассировки и аналитики.

entry.go

TrendEntry

Один элемент топа: Query и Count. JSON tags задают имена полей в ответе: query и count.

errors.go

ErrorCode

Числовой код доменной ошибки. Коды полезны, когда нужно отличать ошибки не только по тексту.

DomainError

Структура ошибки: Code и Message. Метод Error() делает ее обычной Go-ошибкой, потому что реализует интерфейс error.

Is(target error)

Позволяет errors.Is сравнивать ошибки по коду, а не только по одному и тому же указателю. Поэтому ошибка с тем же CodeEmptyQuery считается такой же доменной ошибкой.

CodeOf(err error)

Достает ErrorCode из ошибки, даже если она была обернута через fmt.Errorf("...: %w", err).

Sentinel errors

Переменные ErrEmptyQuery, ErrQueryBlocked, ErrEventOutOfWindow, ErrRateLimited, ErrStopWordNotFound - заранее созданные доменные ошибки. Остальной код может делать errors.Is(err, domain.ErrEmptyQuery).

internal/application/trends

Application слой отвечает за сценарии. Он говорит "что нужно сделать", но не знает деталей "как именно Kafka читает" или "как именно хранилище хранит".

ports.go

TrendsStore interface

Это контракт хранилища. Use case требует методы Add, Top, AddStop, RemoveStop, ListStop, Window.

В production этот интерфейс реализует MemoryStore. В тестах его можно заменить fake/stub.

MetricsSink interface

Контракт метрик. Use case не знает Prometheus, он просто вызывает методы EventAccepted, EventRejected и так далее.

ingest.go

IngestEventCommand

Входная команда для сценария приема события. Сейчас содержит Query и Timestamp.

IngestEventUseCase

Структура хранит зависимости: store и metrics.

Handle(ctx, cmd)

Главная логика ingest:

  1. Нормализовать и проверить query через domain.
  2. Если query плохой - увеличить rejected и вернуть ошибку.
  3. Положить событие в store.
  4. Если store отказал - увеличить rejected и вернуть ошибку.
  5. Если все хорошо - увеличить accepted.

query.go

TopQuery и TopResult

TopQuery - входные параметры запроса топа. TopResult - результат: длина окна и список элементов.

QueryTopUseCase.Handle

Если limit не задан или меньше нуля, ставит default 10. Затем берет окно и top из store.

stoplist.go

StopListUseCase

Управляет стоп-листом. При добавлении и удалении сначала превращает raw string в SearchQuery, чтобы стоп-лист тоже был нормализован. Поэтому "Spam" и " spam " станут одним значением "spam".

internal/adapter/http

HTTP adapter переводит HTTP-запросы в вызовы use case и переводит результат обратно в JSON.

handler.go

Server struct

Хранит use case для top, use case для stop-list и http.ServeMux, который занимается routing.

NewServer

Создает server, инициализирует mux и вызывает routes. Наружу возвращается готовый объект.

routes

Регистрирует endpoints:

RouteЧто делает
GET /health, HEAD /healthПроверка, что сервис жив.
GET /topВернуть топ запросов.
GET /stop-listПоказать стоп-лист.
POST /stop-listДобавить query в стоп-лист.
DELETE /stop-list/{query}Удалить query из стоп-листа.
GET /metricsОтдать Prometheus-метрики.

top

Читает query parameter limit. Если он не число, меньше 1 или больше 1000 - возвращает 400. Затем вызывает use case и пишет JSON.

addStop

Декодирует JSON body вида {"query":"iphone"}. Если JSON плохой - 400. Если query пустой - тоже 400. Если все хорошо - 201.

removeStop

Берет query из path. Если query пустой - 400. Если такого слова нет в стоп-листе - 404. Если удалили успешно - 204 No Content.

writeJSON и writeError

Маленькие helpers, чтобы не повторять установку Content-Type, status code и JSON encoding в каждом handler-е.

internal/adapter/kafka

Kafka adapter читает сообщения из Kafka и передает их в IngestEventUseCase.

consumer.go

Config

Настройки Kafka consumer: список broker-ов, topic и group id.

eventDTO

DTO - Data Transfer Object. Это структура, которая соответствует JSON-сообщению из Kafka. JSON tags говорят, какие имена полей ждать: query, user_id, request_id, timestamp, source.

Consumer struct

Хранит Kafka client, use case, metrics, logger, sync.WaitGroup для ожидания goroutine, sync.Once для безопасного повторного Close и функцию cancel.

Start

Проверяет обязательные настройки, создает kgo.Client, делает отдельный context с cancel, создает Consumer и запускает go c.run(runCtx).

Используется AutoCommitMarks: offsets будут коммититься после того, как код пометит records как обработанные.

run

Бесконечный цикл polling-а Kafka. Он вызывает PollFetches, логирует ошибки fetch-а, проходит по каждому record, обрабатывает его и помечает для commit.

Важно: record помечается после обработки даже если событие malformed или доменно отклонено. Это защищает consumer от вечной остановки на одном плохом сообщении.

handle

Увеличивает EventReceived, пытается распарсить JSON. Если JSON плохой, увеличивает EventMalformed и пишет warning. Если JSON нормальный, вызывает ingest use case.

Close

Безопасно закрывает consumer: отменяет context, ждет goroutine, делает финальный commit отмеченных offsets и закрывает Kafka client.

slogWriter

Adapter, который позволяет franz-go писать свои внутренние логи через slog.

internal/infra/trends

Это самая интересная часть: in-memory sliding-window хранилище.

Идея sliding window

Сервис считает не "за все время", а только за последние WINDOW, например 5 минут. Чтобы быстро удалять старые события, окно разбито на маленькие bucket-ы, например по 1 секунде.

Если окно 5 минут, а bucket 1 секунда, нужно примерно 301 bucket. Каждый bucket хранит счетчики запросов за свою секунду. 

bucket 12:00:00 -> iphone: 2, sneakers: 1
bucket 12:00:01 -> iphone: 4
bucket 12:00:02 -> dress: 1

memory_store.go

var _ apptrends.TrendsStore = (*MemoryStore)(nil)

Compile-time проверка: MemoryStore действительно реализует интерфейс TrendsStore. Если забудут метод, проект не скомпилируется.

Clock

Интерфейс времени. В production используется realClock, в тестах - fake clock. Это позволяет тестировать "прошло 5 минут" без реального ожидания 5 минут.

bucket

Один временной bucket: start - начало интервала, counts - сколько раз встретился каждый запрос в этом интервале.

MemoryStore

Главные поля:

  • mu защищает данные от гонок.
  • window - длина окна.
  • resolution - размер одного bucket-а.
  • buckets - ring buffer bucket-ов.
  • totals - общий счетчик по активному окну.
  • stopList - заблокированные запросы.
  • snapshot - кешированный отсортированный топ.
  • dirty - флаг "snapshot устарел".
  • maxPerBucket - антинакрутка на один query в один bucket.

NewMemoryStore

Проверяет параметры и подставляет defaults, если передали плохие значения. Создает нужное количество bucket-ов и map-ы для totals и stop-list.

Add

Добавляет одно событие:

  1. Проверяет, что query не zero.
  2. Берет mutex.
  3. Проверяет stop-list.
  4. Если timestamp пустой - ставит текущее время.
  5. Если timestamp чуть в будущем - прижимает к now.
  6. Если timestamp старше окна - возвращает ErrEventOutOfWindow.
  7. Вызывает expireLocked, чтобы удалить старые bucket-ы.
  8. Округляет timestamp до начала bucket-а через Truncate.
  9. Считает индекс bucket-а в ring buffer.
  10. Если bucket занят другим временем, вычитает старые значения из totals и переиспользует bucket.
  11. Проверяет rate limit для этого query в этом bucket-е.
  12. Увеличивает счетчик в bucket-е и общий счетчик в totals.
  13. Ставит dirty = true, потому что top теперь может измениться.

Top

Возвращает top-N:

  1. Если limit плохой - ставит 10.
  2. Берет mutex.
  3. Удаляет старые bucket-ы.
  4. Если snapshot dirty - пересобирает его.
  5. Обрезает snapshot до limit.
  6. Возвращает копию, чтобы вызывающий код не мог изменить внутренний slice store-а.

AddStop, RemoveStop, ListStop

Управляют stop-list. Список хранится как map[string]struct{}, потому что нужна быстрая проверка "есть или нет". ListStop сортирует результат, чтобы ответ был стабильным.

expireLocked

Проходит по bucket-ам и удаляет те, чей start старше границы окна. Перед очисткой bucket-а значения вычитаются из totals.

subtractBucketLocked

Для каждого query в bucket-е уменьшает общий счетчик. Если общий счетчик стал нулевым или отрицательным, query удаляется из totals.

rebuildSnapshotLocked

Строит новый список TrendEntry из totals, пропускает stop-list, сортирует по count убыванию, а при равном count - по query по алфавиту. Потом сохраняет в snapshot и сбрасывает dirty.

internal/infra/metrics

Метрики нужны, чтобы понимать состояние сервиса: события приходят или нет, сколько отклоняется, сколько malformed, сколько сервис живет.

prometheus.go

Sink

Хранит счетчики как atomic.Uint64. Atomic нужен, потому что Kafka consumer и HTTP могут работать параллельно.

Методы EventReceived, EventAccepted, ...

Каждый метод просто увеличивает свой счетчик на 1.

HTTPHandler

Возвращает HTTP handler для route /metrics. Он ставит content type Prometheus text format и вызывает write.

write

Печатает метрики в формате Prometheus: сначала комментарии # HELP и # TYPE, потом значение. Также выводит uptime в секундах.

Тесты

В проекте тесты лежат рядом с кодом и имеют суффикс _test.go. Запускаются командой: 

go test ./...
Файл Что проверяет
internal/config/config_test.go Default config, CSV brokers, плохие duration/integer, связь window и resolution.
internal/domain/trends/event_test.go Нормализация query и отклонение пустых строк.
internal/domain/trends/errors_test.go Сравнение доменных ошибок через errors.Is и извлечение кода.
internal/application/trends/ingest_test.go Поведение ingest use case: accepted/rejected и вызовы store.
internal/adapter/http/handler_test.go HTTP endpoints: health, top, limit validation, stop-list.
internal/infra/trends/memory_store_test.go Sliding window, stop-list, rate limit, параллельный доступ.
internal/infra/trends/memory_store_bench_test.go Бенчмарки производительности store.
internal/infra/metrics/prometheus_test.go Prometheus output и atomic increments под параллельной нагрузкой.
Почему в тестах fake/stub? Чтобы тестировать use case без настоящей Kafka, настоящего HTTP сервера или реального времени. Это делает тесты быстрыми и предсказуемыми.

Docker и docker-compose

Dockerfile

Build stage

Первая стадия использует golang:1.24-alpine, скачивает зависимости и собирает бинарник: go build ... -o /bin/search-trends ./cmd.

Runtime stage

Вторая стадия использует маленький alpine:3.20. В нее копируется только готовый бинарник. Приложение запускается не от root, а от пользователя app.

docker-compose.yml

kafka

Поднимает Kafka в KRaft-режиме без отдельного Zookeeper. Healthcheck проверяет, что Kafka отвечает на список топиков.

app

Собирает приложение из текущего Dockerfile, передает ENV, пробрасывает порт 8080 и ждет healthy Kafka.

Скрипты

scripts/produce.sh

Публикует много событий в Kafka. Обычно принимает количество событий и число уникальных запросов. Нужен для ручного наполнения сервиса данными.

scripts/loadtest.sh

Делает простой нагрузочный сценарий: сначала публикует события, потом бьет endpoint /top через hey. Это помогает увидеть, как сервис ведет себя под чтением.

Как читать этот проект самому

  1. Начни с README.md, чтобы понять внешнее поведение сервиса.
  2. Потом открой cmd/main.go: там видно, какие части вообще существуют.
  3. Перейди в internal/domain/trends: там самые базовые понятия.
  4. Открой internal/application/trends: там сценарии без инфраструктурного шума.
  5. Посмотри adapter-ы: HTTP показывает API, Kafka показывает входной поток.
  6. После этого разбирай MemoryStore: он самый алгоритмический.
  7. В конце читай тесты: они показывают ожидаемое поведение лучше любой устной договоренности.
Главный вывод: проект построен так, чтобы бизнес-логика была отделена от транспорта. Kafka и HTTP находятся по краям, domain и application - в центре, а конкретное хранилище и метрики подключаются как реализации интерфейсов.
