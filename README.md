# Search Trends

Сервис для виджета "Сейчас ищут". Он читает поток поисковых событий из NATS и отдает топ популярных поисковых запросов за последние 5 минут через HTTP API.

## Быстрый запуск

```bash
docker compose up --build
```

Проверка, что сервис поднялся:

```bash
curl http://localhost:8080/health
```

Пример ответа:

```json
{"status":"ok"}
```

Отправить несколько поисковых событий в NATS:

```bash
docker compose exec nats-box nats pub --server nats://nats:4222 search.events '{"query":"iphone 15","user_id":"u1","request_id":"r1","timestamp":"'"$(date -u +%Y-%m-%dT%H:%M:%SZ)"'","source":"search-api"}'
docker compose exec nats-box nats pub --server nats://nats:4222 search.events '{"query":"iphone 15","user_id":"u2","request_id":"r2","timestamp":"'"$(date -u +%Y-%m-%dT%H:%M:%SZ)"'","source":"search-api"}'
docker compose exec nats-box nats pub --server nats://nats:4222 search.events '{"query":"sneakers","user_id":"u3","request_id":"r3","timestamp":"'"$(date -u +%Y-%m-%dT%H:%M:%SZ)"'","source":"search-api"}'
```

Получить топ запросов:

```bash
curl 'http://localhost:8080/top?limit=10'
```

Пример ответа:

```json
{
  "items": [
    {
      "query": "iphone 15",
      "count": 2
    },
    {
      "query": "sneakers",
      "count": 1
    }
  ],
  "window": "5m0s"
}
```

## HTTP API

`GET /health`

Проверка состояния сервиса.

`GET /top?limit=10`

Возвращает топ запросов за последние 5 минут. Параметр `limit` ограничен диапазоном от `1` до `1000`.

`GET /stop-list`

Возвращает текущий стоп-лист.

`POST /stop-list`

Добавляет запрос в стоп-лист без перезапуска сервиса.

```bash
curl -X POST http://localhost:8080/stop-list \
  -H 'Content-Type: application/json' \
  -d '{"query":"iphone 15"}'
```

`DELETE /stop-list/{query}`

Удаляет запрос из стоп-листа.

```bash
curl -X DELETE http://localhost:8080/stop-list/iphone%2015
```

`GET /metrics`

Возвращает базовые метрики в Prometheus-формате.

```bash
curl http://localhost:8080/metrics
```

## Контракт события

Сервис ожидает JSON-сообщения в NATS subject `search.events`.

```json
{
  "query": "iphone 15",
  "user_id": "u123",
  "request_id": "req-456",
  "timestamp": "2026-05-22T12:00:00Z",
  "source": "search-api"
}
```

Обязательное поле:

- `query` - исходный поисковый запрос пользователя. Сервис нормализует его: обрезает пробелы, приводит к нижнему регистру и схлопывает повторяющиеся пробелы.

Дополнительные поля:

- `timestamp` - время события. Нужно, чтобы корректно учитывать события при небольшой задержке доставки из брокера.
- `user_id` - стабильный идентификатор пользователя. В текущей реализации не используется, но нужен для развития антифрод-логики: per-user лимиты, анализ накруток, дедупликация.
- `request_id` - идентификатор запроса для трассировки и потенциальной идемпотентности.
- `source` - имя сервиса-источника, полезно для отладки и метрик по производителям событий.

## Архитектура

Хранилище сделано in-memory, потому что виджету нужны быстрые чтения, а задача не требует долговременной аналитики. Основная структура данных - скользящее окно, разбитое на бакеты по времени. По умолчанию окно равно 5 минутам, размер бакета - 1 секунда.

Каждый бакет хранит счетчики по нормализованному запросу. Дополнительно сервис держит суммарные счетчики по всему активному окну. Когда бакет устаревает или переиспользуется, его значения вычитаются из общих счетчиков. За счет этого не нужно хранить и пересканировать все отдельные события.

Чтений топа ожидается заметно больше, чем входящих событий. Поэтому `/top` возвращает кэшированный отсортированный snapshot. Snapshot пересобирается только после записи нового события, истечения бакетов или изменения стоп-листа.

Стоп-лист применяется динамически. Заблокированные запросы сразу скрываются из топа, а новые события с такими запросами не принимаются. Исторические счетчики остаются в памяти, поэтому если запрос удалить из стоп-листа, он снова может появиться в топе, пока его события еще находятся внутри 5-минутного окна.

## Защита от накруток

В постановке задачи отдельно упомянуты аномальные всплески от конкурентов или парсеров. В текущей версии реализована простая защита: ограничение количества одинаковых нормализованных запросов, которые могут попасть в один временной бакет.

По умолчанию лимит равен `1000` одинаковых запросов в секунду и настраивается через переменную окружения:

```bash
MAX_QUERY_PER_BUCKET=1000
```

Это не полноценный антифрод, но такая мера защищает виджет от грубых всплесков одного запроса и не усложняет критический путь обработки событий.

## Компромиссы

- Данные хранятся в памяти. При перезапуске сервиса текущее 5-минутное окно теряется. Для виджета это может быть приемлемо; если нет, можно добавить восстановление из брокера или компактное внешнее хранилище.
- Snapshot топа пересортировывает все уникальные запросы активного окна. Это простой и предсказуемый подход. При очень высокой кардинальности можно заменить его на heap или approximate heavy hitters.
- Ограничение одинаковых запросов в бакете снижает влияние накрутки, но может недосчитать реально вирусный запрос на пике. В production-версии лучше добавить лимиты по `user_id`, session id, IP/fingerprint или другим признакам.
- События старше активного окна игнорируются. События с timestamp сильно из будущего считаются как текущие, чтобы не ломать окно.

## Тесты

```bash
go test ./...
```

Покрыта ключевая бизнес-логика:

- подсчет топа внутри скользящего окна;
- удаление устаревших бакетов;
- фильтрация через стоп-лист;
- ограничение одинаковых запросов в одном бакете.

## Нагрузочная проверка

После запуска сервиса можно проверить ручку чтения, например через `hey`:

```bash
hey -z 30s -c 100 'http://localhost:8080/top?limit=10'
```

Для более точной проверки можно добавить Go-бенчмарки вокруг `internal/trends.Store` с ожидаемым количеством уникальных запросов.
